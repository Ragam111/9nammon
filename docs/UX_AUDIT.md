# UX/UI Audit — 2026-11-20

สถานะ: 11 ข้อ high แก้แล้วและเทสต์ผ่าน (138 เทสต์ UI) ส่วนข้อ medium 32 และ low 13 ยังไม่ได้แก้

Static read-only audit (4 reviewers). Findings are unverified until fixed; line numbers are from commit dc005ee.

## entry

The shared app.css token system is well built: light and dark themes, focus-visible rings and reduced-motion support. But install.html ignores it completely, and the chat page has real interaction bugs: Enter still sends while a reply is streaming, todo failures are silent, todos cannot be toggled by keyboard, and on phones the input bar scrolls out of view. On all three pages the form controls rely on placeholders or headings instead of real labels, and some feedback, such as raw JS error text and a copy button that stays failed, is missing or confusing.

- **[high] `app/index.html:146`** (feedback-states) The Enter key handler calls sendMessage() without checking whether a request is in flight. sendMessage only disables #send-btn (line 79) and never checks a busy flag, so pressing Enter while a reply streams starts a second concurrent /api/chat/stream request. — **แก้แล้ว** (ยังไม่ commit)
  - Impact: Pressing Enter during a slow reply on a weak laptop sends a second message. Two replies then stream into separate bubbles, the history array interleaves user and assistant turns in the wrong order, and the 'thinking' notes get removed unpredictably.
  - Fix: Add a module-level `let busy = false;`. Return early from sendMessage when busy is true, set it to true at start and false in finally. Optionally also set inputEl.readOnly while streaming.
- **[high] `app/app.css:197`** (responsive) At ≤720px body.page-chat becomes `height:auto; min-height:100%` and #main gets only `min-height:55vh` (line 200), so nothing bounds the height of #chat (flex:1; overflow-y:auto). The chat log grows the whole page instead of scrolling inside itself. `chatEl.scrollTop = chatEl.scrollHeight` (index.html 71, 128) then does nothing because #chat has no overflow. — **แก้แล้ว** (ยังไม่ commit)
  - Impact: On a phone (~375px), after a few messages the #input-bar is pushed below the fold and new streamed tokens appear off-screen. The user has to scroll the page manually to read the reply and to type again.
  - Fix: Keep the chat column at viewport height on mobile, for example `body.page-chat{height:100dvh}` with `#main{flex:1;min-height:0}`. Make the sidebar an overlay or put it above #main when expanded, so #chat stays the only scroll container.
- **[high] `app/index.html:198`** (feedback-states) toggleTodo, deleteTodo and the add-todo handler (lines 198, 211, 228) never check res.ok. Errors such as 401, 429 or 500 are ignored and only network exceptions reach console.error. The add handler also clears the input (line 226) before the request succeeds. — **แก้แล้ว** (ยังไม่ commit)
  - Impact: If the token has expired or the server rejects the request, the user's typed todo disappears and nothing on screen says it was not saved. Toggle and delete clicks also appear to do nothing.
  - Fix: Check `if (!res.ok)` and call setTodoMsg('เพิ่ม/ลบ/อัปเดต todo ไม่สำเร็จ (' + res.status + ')', true). Clear todoInput only after success, and use setTodoMsg in the catch blocks instead of console.error.
- **[high] `app/index.html:177`** (accessibility) Todos are toggled by a click listener on a plain <span> (lines 177-180) with no tabindex, role or key handler. The delete control is an emoji-only button (line 182) whose only name is title='ลบ'. — **แก้แล้ว** (ยังไม่ commit)
  - Impact: Keyboard and screen-reader users cannot mark a todo done at all. The delete button is announced only as 'ลบ' with no indication of which todo it removes.
  - Fix: Render each todo as a <label><input type=checkbox> text</label> or a <button aria-pressed>. Give the delete button aria-label='ลบ todo #' + t.id.
- **[high] `app/install.html:84`** (accessibility) The OS switcher tabs are <div class="tab"> elements with only click listeners (lines 84-85, 148-156). They have no tabindex, no role=tab or aria-selected, and no keyboard handling. — **แก้แล้ว** (ยังไม่ commit)
  - Impact: Keyboard-only users cannot reach the Linux / macOS / WSL install command at all, and screen readers do not know these are switchable tabs.
  - Fix: Use <button type="button" role="tab" aria-selected aria-controls="cmd-win|cmd-nix"> inside a role="tablist" container and update aria-selected in the click handler.
- **[medium] `app/install.html:8`** (consistency) install.html does not load /app.css. It defines its own token set (--bg, --card, --accent:#2563eb blue, link colour #7aa2ff at line 43) and forces `color-scheme: dark` with no light theme. Every other page uses the green --lca-accent with light and dark variants.
  - Impact: The landing and install page looks like a different product: blue buttons, dark-only colours and different radii. Users in light mode see a jarring switch when they click through to /login or / (lines 134-135).
  - Fix: Link /app.css and map the page's classes onto --lca-* tokens (for example .btn uses --lca-accent and --lca-accent-fg, .card uses --lca-surface and --lca-r-lg). Drop the local :root block and the forced dark color-scheme.
- **[medium] `app/install.html:64`** (ux-copy) The Windows paths are written as `%LOCALAPPDATA%\\LocalCodeAssistant\\data` (line 64) and `%LOCALAPPDATA%\\LocalCodeAssistant\\` (line 75). HTML does not process escape sequences, so the page shows doubled backslashes.
  - Impact: Users who copy the data or install path into Explorer or a terminal get a malformed path with doubled backslashes, and the instructions look broken.
  - Fix: Use single backslashes in the HTML text: %LOCALAPPDATA%\LocalCodeAssistant\data.
- **[medium] `app/install.html:162`** (feedback-states) The copy button calls navigator.clipboard.writeText directly. When the page is served over plain http on a LAN IP (not a secure context), navigator.clipboard is undefined and the call throws synchronously, so the .catch never runs. On a rejected promise the label changes to 'คัดลอกไม่ได้' (line 165) and is never reset.
  - Impact: Clicking Copy either does nothing silently or leaves the button stuck on the failure label, with no fallback for selecting the text.
  - Fix: Guard with `if (!navigator.clipboard) { select the text range; show 'กด Ctrl+C เพื่อคัดลอก'; }`, wrap the call in try/catch, and restore the label after a timeout in the failure path too.
- **[medium] `app/install.html:24`** (responsive) .cmd is `position:relative; overflow-x:auto; white-space:pre`, and the .copy button inside it is `position:absolute; right:8px`. An absolutely positioned child of a scroll container scrolls with the content, and the long one-line commands (lines 88, 92) overflow at 375px.
  - Impact: On a phone, swiping to read the rest of the command moves the Copy button off-screen or over the command text, so the main action is hard to find.
  - Fix: Put the command in an inner <code> that scrolls (`overflow-x:auto`) and keep the button outside the scroll area. For example, make .cmd a flex row with the scrolling code at flex:1 and the button flex:none.
- **[medium] `app/login.html:24`** (accessibility) The username, password and API-key inputs (lines 24, 25, 33) have only a placeholder and no <label> or aria-label. The error paragraph #err (line 28) and #status (line 20) are not live regions. On index.html, #model-select, #lang-select and #todo-input (lines 13, 21, 27) are likewise unlabeled, because the h2 headings are not associated with them.
  - Impact: Screen readers announce the fields as unnamed edit boxes or combo boxes, the label disappears once the user starts typing, and login errors are not announced when they appear.
  - Fix: Add a visible <label for> to each field (or aria-label on the sidebar controls), add role="alert" to #err, and add aria-live="polite" to #status.
- **[medium] `app/app.js:51`** (ux-copy) login() calls res.json() without a fallback, and the catch block sets `this.lastError = String(e)`. login.html (line 96) then shows that string to the user, so a proxy error or HTML 502 page, or a network failure, produces raw text such as 'SyntaxError: Unexpected token <' or 'TypeError: Failed to fetch'.
  - Impact: When the server is down, users see raw English JavaScript exception text instead of a Thai message saying the server cannot be reached.
  - Fix: Use `var data = await res.json().catch(function(){return {};});`. In the catch block set lastError to 'ต่อเซิร์ฟเวอร์ไม่ได้ — ตรวจว่า LCA เปิดอยู่'. Map 401 and 429 to friendly Thai text.
- **[medium] `app/app.css:162`** (navigation) #main-head is `display:none` by default and shown only at ≤720px (line 198). It holds the only navigation link on the chat page, 'Chat Hub' (/chat, index.html line 36). There is also no link to /login, no logout and no signed-in indicator, and a 401 chat error (index.html 101) gives no path to sign in.
  - Impact: Desktop users have no way to reach Chat Hub or the login page from the main chat screen. When a token expires they see '[error] ...' with no next step.
  - Fix: Always show a slim header with the title, the Chat Hub link and a login or account link. Hide only the ☰ toggle on desktop. On 401, append a link to /login?next=/.
- **[medium] `app/index.html:38`** (accessibility) #chat has no role="log" or aria-live, and the '(กำลังคิด...)' note and streamed assistant text are injected silently. The send button also gives no busy indication other than opacity.
  - Impact: Screen-reader users are not told that the assistant is thinking, that a reply has arrived, or that an error note was added.
  - Fix: Add role="log" aria-live="polite" to #chat. Announce the final reply once at stream end rather than on every token, for example through a visually hidden live region, and set aria-busy on #chat while streaming.
- **[low] `app/login.html:50`** (consistency) The secondary and danger button variants are written as inline styles (`background:var(--lca-surface-2); color:var(--lca-fg); border-color:var(--lca-line)` on line 50, and the same with --lca-bad on line 51). app.css already has .lca-btn variants but no secondary or danger class, and the header and main also use inline styles (lines 13, 16, 22, 23, 32).
  - Impact: Secondary buttons drift from the design system, and the hover and focus styles of .lca-btn do not apply, so these buttons have no hover feedback.
  - Fix: Add .lca-btn.secondary and .lca-btn.danger to app.css and use them here. Move the layout inline styles into .page-dev utility classes.
- **[low] `app/app.css:24`** (accessibility) In light mode, primary buttons (#send-btn at line 191, .page-dev button at line 219, .lca-btn.primary) put white --lca-accent-fg on --lca-accent #1f8a4c, which is about 4.4:1. The text is 14px semibold, which does not count as large text, so it falls just below WCAG AA 4.5:1.
  - Impact: The main 'ส่ง' and 'เข้าสู่ระบบ' button labels are slightly low-contrast for low-vision users or on dim netbook screens.
  - Fix: Darken the light-theme accent slightly, for example #1a7a43 (about 5.3:1 with white), or bump the button font to 15px bold or larger.
- **[low] `app/install.html:113`** (ux-copy) The pages spell 'chat' two ways: install.html uses 'แชท' (lines 113, 119, 135) and also 'แชต' (line 56), while login.html uses 'แชต' (lines 40, 49). index.html's status bar (line 39) also says the model runs only through local Ollama, while install.html (line 63) advertises a cloud mode with an API key.
  - Impact: Inconsistent spelling and contradictory statements about whether data leaves the machine undermine trust in the privacy messaging.
  - Fix: Pick one spelling (แชท is the common form) across all pages. Make the status-bar text reflect the active backend, or word it neutrally, for example 'โหมด local: รันผ่าน Ollama ในเครื่อง'.

## chat

The chat hub works as a feature, but in practice it is fragile. Almost every secondary action (search, folders, persona, export, import, branch switch, ephemeral save) awaits fetch with no try/catch, so failures are silent. The chat page also inherits conflicting .msg and font rules from app.css, and has light-only hardcoded colours that break dark mode. spaces.html ignores the design tokens completely: its colours are hardcoded for a dark theme, so items are unreadable in light mode, it has no mobile layout, its clickable rows are not keyboard-accessible, and none of its inputs have labels.

- **[high] `app/spaces.html:17`** (visual) Spaces styles hardcode dark-theme colours (.item background #22262f, .space-item:hover #22262f, borders #2a2e37, active #2563eb) instead of the --lca-* tokens. In light mode, body text uses --lca-fg #1b201a, so it ends up on a near-black #22262f bubble. — **แก้แล้ว** (ยังไม่ commit)
  - Impact: In the default light theme, message text in spaces is dark-on-dark and almost impossible to read. The blue active state also does not match the green accent used everywhere else.
  - Fix: Replace the hex values with var(--lca-surface-2), var(--lca-line), var(--lca-accent-weak) or var(--lca-accent) with var(--lca-accent-fg), and var(--lca-bad) for .err.
- **[high] `app/chat.js:614`** (feedback-states) Many async handlers await api() with no try/catch: doSearch (614), add-folder (699), persona change (708), export (716), import (727-733, including JSON.parse of the user file), folder change (737), ephemeral save (676), and switchTo/openConv from list and sibling clicks (566, 178). A rejected promise only reaches the console. — **แก้แล้ว** (ยังไม่ commit)
  - Impact: When the server is down, a session has expired (401), or an imported file is invalid, the button does nothing and the user gets no message. Unsaving ephemeral mode can lose the temporary chat with no warning.
  - Fix: Wrap each handler with a helper such as safe(fn) that catches the error and calls setNotice(err.message). For import, show a specific message like 'ไฟล์ไม่ใช่ JSON ที่ถูกต้อง' and reset import-file.value so the same file can be chosen again.
- **[medium] `app/chat.css:94`** (visual) .banner.warn uses a hardcoded light background #f8e7c8, while the text colour comes from --lca-fg. In dark mode that token is #e7ece4 (near-white).
  - Impact: Every error or notice shown through setNotice (the main error channel on the page) is near-white text on a pale yellow background in dark mode, so it is unreadable.
  - Fix: Use a token-based warn surface, for example add --lca-warn-weak to both theme blocks in app.css, or use background: var(--lca-surface-2); border-left: 3px solid var(--lca-warn).
- **[medium] `app/app.css:171`** (consistency) app.css defines a global .msg bubble (fit-content, max-width 720px, padding, border, background, white-space pre-wrap) and .msg.user with margin-left:auto, all meant for index.html. chat.html renders <article class="msg"> and adds its own bubble on .msg.user .body (chat.css:99).
  - Impact: User messages in the chat hub show a bubble inside a bubble (two borders and two blue backgrounds). Assistant messages shrink to fit-content cards with an extra border, unlike the flat layout chat.css intends. The compare grid ends up nested inside a narrow card.
  - Fix: Scope the index-page rules in app.css (body.page-chat .msg …), or rename the chat-hub class (e.g. .hub-msg) so the two stylesheets stop colliding.
- **[medium] `app/chat.css:24`** (consistency) chat.css redefines the design tokens --lca-sans and --lca-mono and loads three webfonts. It also sets body to 16px/1.7, while app.css uses 14px/1.5 with system fonts (app.css:6 states the rule 'ฟอนต์ระบบล้วน').
  - Impact: The chat hub uses a different typeface and size than spaces.html, index and dev, so moving between pages feels like switching apps. It also adds font downloads on the low-RAM target machine.
  - Fix: Remove the token overrides. If IBM Plex Thai is wanted, add it to the app.css tokens for every page. Otherwise keep system fonts and drop the @font-face blocks and the preload in chat.html:7.
- **[medium] `app/chat.css:73`** (responsive) .head is display:flex with no flex-wrap and holds a title plus 6 controls (model select, compare, persona select, export, import, and sometimes custom-model). The 720px media query only collapses the grid; the header gets no changes.
  - Impact: At ~375px the header controls overflow sideways and are clipped (.main has min-width:0), or they cause horizontal scroll, so export and import can become unreachable on a phone.
  - Fix: Add flex-wrap: wrap to .head and give .title flex: 1 1 100% under 720px, or move export, import and compare into an overflow menu on small screens.
- **[medium] `app/spaces.html:10`** (responsive) The spaces layout is a fixed 260px sidebar next to the main column inside height:calc(100vh - 80px), and there is no media query.
  - Impact: On a 375px phone the message column is only about 100px wide, so the composer input and messages become unusable.
  - Fix: Add @media (max-width:720px) { .layout { flex-direction: column; height: auto } .sidebar { width: 100%; border-right: 0; max-height: 40vh } }, matching chat.css.
- **[medium] `app/spaces.html:71`** (accessibility) Space rows are <div class="space-item"> elements with only a click listener: no tabindex, no role and no key handler. The active state is shown only by colour (.active).
  - Impact: Keyboard and screen-reader users cannot open a space at all, which blocks the whole page for them.
  - Fix: Render the rows as <button type="button"> (as chat.js does for conversations) and set aria-current="true" on the selected one.
- **[medium] `app/spaces.html:32`** (accessibility) #new-name, #new-vis and #msg have no <label> or aria-label; the inputs rely on a placeholder only. In chat.html, #search (line 17) and the composer #input textarea (line 45) also have no accessible name beyond the placeholder.
  - Impact: Screen readers announce unnamed edit fields, and the placeholder hint disappears as soon as the user starts typing.
  - Fix: Add aria-label values (e.g. 'ชื่อพื้นที่ใหม่', 'การมองเห็น', 'ข้อความ', 'ค้นหาแชท', 'ข้อความถึงโมเดล') or visually-hidden <label> elements.
- **[medium] `app/spaces.html:102`** (feedback-states) send() clears the input before the POST and never disables #send or #msg while the request is in flight. The create button (113-123) also has no busy state. On an error, the text the user typed is gone.
  - Impact: A failed send silently throws away the user's message, and double-clicking sends or creates duplicates.
  - Fix: Disable the button during the request and clear the input only after res.ok. On error, restore the text and show showErr.
- **[medium] `app/chat.js:639`** (feedback-states) Pressing ArrowUp in an empty composer silently enters edit mode (S.editId) with no visual indicator and no way to cancel. Branch mode (321-324) only changes the placeholder, which is hidden once typing starts. Neither mode has a cancel control.
  - Impact: The user may think they are sending a new message, but they are actually rewriting an earlier one and creating a new version, which is confusing and hard to undo.
  - Fix: Show a dismissible chip above the composer, such as 'กำลังแก้ข้อความ… ✕' or 'แตกสาขาจากข้อความนี้ ✕', that clears editId and branchFrom, and also clear these modes on Escape.
- **[low] `app/chat.html:43`** (accessibility) #thread and #notice have no aria-live or role="status". The Send button changes to 'หยุด' while streaming with no announcement. The copy buttons (chat.js:211, 329) give no feedback after copying.
  - Impact: Screen-reader users do not hear streamed replies, errors or the stop state. Sighted users cannot tell whether copy worked.
  - Fix: Add role="status" aria-live="polite" to #notice and aria-live="polite" aria-busy toggled on #thread. After writeText resolves, change the button text to 'คัดลอกแล้ว' for about 1.5s.
- **[low] `app/chat.js:714`** (feedback-states) The export button returns silently when there is no conversation (if (!S.conv) return;), and the button is never disabled. The same silent return happens in regen and switchTo.
  - Impact: On a new chat, clicking 'ส่งออก' does nothing, and it looks broken.
  - Fix: Disable #export-btn whenever S.conv is null (update it in openConv and in the new-chat handler), or call setNotice('ยังไม่มีแชทให้ส่งออก').
- **[low] `app/chat.js:415`** (feedback-states) The assistant draft is rendered with empty content until the first SSE delta arrives. There is no thinking or loading indicator, and boot() shows nothing while it loads providers and lists.
  - Impact: With a slow local Ollama the first token can take several seconds, so the reply area looks blank and frozen.
  - Fix: Render a placeholder such as 'กำลังคิด…' (app.css already has .system-note.thinking) in the draft body until the first delta. Show 'กำลังโหลด…' in #conv-list during boot.
- **[low] `app/spaces.html:27`** (navigation) spaces.html uses class="topbar", which no stylesheet defines, so it does not share the chat hub's header or sidebar. The back link reads 'กลับหน้าแชต' while chat.html spells it 'แชท', and chat.html (line 26) has no link to /spaces. Copy across the two pages also mixes English, for example the 'persona' placeholder (chat.html:36) and 'บริษัท (shared)'.
  - Impact: The two pages feel unrelated, spaces cannot be found from the chat hub, and the inconsistent Thai spelling and mixed English labels look unfinished.
  - Fix: Add a /spaces link in .side-foot. Style a shared header in app.css. Standardise on 'แชท' and use Thai labels such as 'บุคลิก' instead of 'persona'.

## ops

The three admin pages don't look or behave like one product. console.html ignores app.css completely and ships its own dark-only theme with a yellow accent. dev.html follows the shared tokens but hardcodes dark-theme hex colors inline, so its light-mode default looks wrong. Only support.html uses the shared design system cleanly. The most serious problems are: console.html has no visible keyboard focus, dev.html has an irreversible "approve" action with no confirmation, and most fields are labelled only by placeholders. Feedback is also uneven: submit buttons are not disabled while saving, errors show in one place at the top of the page, nothing tells screen readers about status changes, and wide tables overflow at 375px.

- **[high] `app/console.html:29`** (accessibility) `.nav button{all:unset}` (line 29) and `button.btn{all:unset}` (line 46) remove the browser focus ring. console.html does not load app.css, so the shared `:focus-visible` outline (app.css line 127) never applies, and the page's inline <style> defines no replacement. — **แก้แล้ว** (ยังไม่ commit)
  - Impact: Keyboard users cannot see which nav item, Save, Delete or Run button has focus, so the console is effectively unusable without a mouse.
  - Fix: Add `button.btn:focus-visible, .nav button:focus-visible, input:focus-visible, select:focus-visible, textarea:focus-visible { outline: 2px solid var(--accent); outline-offset: 1px; }`, or better, link /app.css and use `.lca-btn`.
- **[high] `app/console.html:8`** (consistency) console.html defines its own private tokens (`--bg:#0a0a0b`, `--accent:#d8e24a` yellow, `--accent2`) and its own font stack, and never links /app.css. dev.html and support.html use the `--lca-*` tokens with a green accent (`--lca-accent:#1f8a4c` / `#45c074`). The console is also dark-only: it has no `prefers-color-scheme` handling, while app.css defaults to light. — **แก้แล้ว** (ยังไม่ commit)
  - Impact: Going from Console to Dev or Support switches theme (dark to light), accent color (yellow to green), button style and fonts. It feels like a different app, and users on a light OS theme get a forced dark console.
  - Fix: Remove the private :root block, link /app.css, map `.card`/`.btn`/`.pill` onto the `--lca-*` tokens (or move them into app.css as shared components) and drop the hardcoded hexes (`#000`, `#7dd3fc`, `#d8b4fe`, `#6b6b74`).
- **[high] `app/dev.html:412`** (feedback-states) The approve button for an agent approval ('อนุมัติ (ลงมือจริง)', which actually writes a file or runs a command) calls decideApproval() (line 429) straight away, with no confirm() and no disabled state while the request is in flight. In contrast, rollback (line 341) does ask for confirmation. — **แก้แล้ว** (ยังไม่ commit)
  - Impact: One misclick, or a double-click, runs an irreversible command or file write, and the admin cannot back out.
  - Fix: Show a confirm() that includes the command or path. Disable both approve and reject buttons for that item while the POST is pending. Show a success message ('อนุมัติแล้ว') before reloading the list.
- **[medium] `app/console.html:148`** (accessibility) None of the form `<label>`s have `for=` attributes and none wrap their inputs (e.g. line 148 `<label>ชื่อ</label><input id="con-name">`; the same pattern repeats at lines 156-159, 184-211, 234-237, 255-256, 290-293). The token input (line 113) has only a placeholder. In support.html, all fields (lines 22, 23, 29, 30, 42) rely on placeholders only. dev.html line 14 and the cluster/eco inputs (lines 95-108) are the same.
  - Impact: Screen readers announce these fields as unlabelled edit boxes. Placeholder-only fields also lose their hint as soon as the user types, which is a problem in long forms like Skills and ecosystem settings.
  - Fix: Add `for="con-name"` etc. to each label, or wrap the input inside its label. Give placeholder-only inputs and selects a visible label or an `aria-label` (support.html #subject/#kind/#channel/#body/#filter-status, the per-row status selects, and the dev.html token/cluster/eco/mb inputs).
- **[medium] `app/console.html:455`** (feedback-states) The Save handlers (con-save line 455, skl-save line 515, bot-save line 567), Run (run-go line 606) and Send (pg-go line 628) never disable their button and never show a success message. After a save, the form just resets silently. In chat-mode Run and in Playground, the output box is cleared and stays empty until the first streamed token arrives, with no 'กำลังรัน...' indicator (that indicator exists only in agent mode, line 613).
  - Impact: Users double-click and create duplicate connections, skills or bots. They can't tell whether a save worked, and a slow model looks frozen.
  - Fix: Disable the button and change its label to 'กำลังบันทึก…' / 'กำลังรัน…' during the await, then re-enable it in `finally`. After a save, show a short success note ('บันทึกแล้ว ✓'). Set the output box to a 'กำลังรอคำตอบ…' placeholder before streaming starts.
- **[medium] `app/console.html:116`** (feedback-states) Every error from every panel goes into the single `#err` div at the top of `<main>` (line 116, via showErr at line 319). Nothing clears it when the user switches panels (go() at line 361), and it has no `role=alert` or `aria-live`. The same pattern is used for dev.html `#error` (line 20), and for support.html `#submit-msg` (line 34), which is styled as muted grey `.note` text even when it reports a validation error (line 74).
